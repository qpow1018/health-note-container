# 001. 홈 운동 완료 체크 반응 지연

- 등록일: 2026-10-19
- 관련: 웹 홈 화면, 같은 화면을 제공하는 앱 WebView
- 조사 기준: `d25f5ab27837c4da34945f402bb7e419e6643db5`. 조사 시작 시 작업 트리 깨끗함.
- 최초 조사 범위: 이슈 등록과 코드·기존 테스트 조사. 이후 사용자 요청으로 제품 코드를 수정했으며 아래에 기록한다. 운영 데이터 변경 없음.

## 제보와 재현 조건

사용자 제보: 홈에서 운동 완료 여부를 체크할 때 반응이 느리다.

확인할 순서: 로그인 → 오늘 예정된 루틴이 있는 홈 → 운동 완료 체크 또는 해제 → 표시 변경과 다른 운동 조작 가능 시점 확인.
기대: 입력 후 완료 여부를 빠르게 인지하고 다음 운동을 조작할 수 있다.
실제: 사용자는 체크 표시가 늦게 바뀐다고 확인했다. `http://localhost:5173/`에서는 느리다는 느낌이 없지만 실제 앱에서는 느리게 느껴진다고 답했다. 전체 화면 멈춤은 보고되지 않았다. 기기 모델·앱의 실제 연결 주소와 배포 버전·네트워크·발생 빈도·지연 시간·체크와 해제의 차이는 미확인이다.

로컬과 앱의 비교는 환경이 통제된 측정이 아닌 사용자 체감이다. [Vite 설정](../../health-note/vite.config.ts)은 development에서 로컬 Supabase를 요구하며, [앱](../../health-note-app/App.tsx)은 `EXPO_PUBLIC_WEB_URL`을 불러온다. 앱 주소에는 코드상 기본값이 없다. 따라서 로컬 DB와 클라우드 DB의 왕복 시간 차이가 드러났을 가능성은 있지만, 설치된 앱의 실제 연결 환경을 확인하기 전에는 확정할 수 없다. 같은 휴대폰·같은 네트워크에서 앱이 불러오는 동일한 웹 주소를 브라우저로 열어 비교해야 네트워크·서버 환경 차이와 WebView 차이를 좁힐 수 있다.

## 수정 전 구현에서 확인한 사실

1. [HomeRoutines](../../health-note/src/features/routine/homeRoutines/HomeRoutines.tsx)의 체크 상태와 진행률은 조회된 `progress`로만 계산한다. 클릭 직후 해당 값을 바꾸는 처리는 없다.
2. `handleExerciseCompleted`는 `isSaving`을 켜고 mutation을 기다린다. 모든 체크박스가 같은 `disabled={isSaving}`을 사용하므로 한 운동 저장 중 다른 루틴·운동의 체크도 잠긴다. 다른 화면 전체가 정지한다는 근거는 없다.
3. [routineQuery](../../health-note/src/queries/routineQuery.ts)의 `useSetExerciseCompleted`는 저장 성공 후 완료 기록 키 전체를 무효화하고 그 Promise를 반환한다. 현재 활성화된 날짜 조회가 다시 수행되며, 정상 흐름에서는 저장과 후속 조회가 끝날 때까지 호출부의 대기가 이어진다. 낙관적 캐시 갱신은 없다.
4. [완료 API](../../health-note/src/api/routine/index.ts)는 체크 시 `routine_progress`에 upsert, 해제 시 delete를 수행한다. 이후 화면용 기록은 별도 GET으로 조회한다. 따라서 클릭부터 확정된 화면 변경까지 저장 요청과 재조회가 순차적으로 필요하다.
5. [앱 WebView](../../health-note-app/App.tsx)의 메시지 처리는 history 연동이며, 완료 저장을 네이티브로 중계하는 경로는 확인되지 않았다. 우선 웹 공통 흐름이 조사 대상이다. 앱 고유 지연이 없다는 뜻은 아니다.

관련 경로의 최근 Git 기록은 통합 가져오기 커밋 `d49bbbb`이다. 현재 구현이 지연을 허용한 이유나 사용자 합의를 증명하지는 않는다.

## 가설과 확인 범위

| 가설 | 확인 방법 및 결과 |
| --- | --- |
| 서버 응답 대기가 체크 표시 지연으로 드러난다 | 코드상 확인. 화면 상태가 저장 후 GET에 의존한다. 사용자 환경에서의 실제 요청 시간은 미측정이다. |
| 전체 체크 잠금이 연속 조작의 체감 지연을 키운다 | 코드상 확인. 모든 체크박스가 하나의 저장 상태를 공유한다. |
| DB 처리 자체 또는 네트워크가 비정상적으로 느리다 | 미확인. 운영 요청 타이밍·DB 실행 계획·실기기 재현을 수집하지 않았다. |
| 화면 계산이나 WebView가 주된 병목이다 | 미확인. 렌더링 프로파일과 실기기 비교가 없다. 네트워크 의존 구조만으로 다른 병목을 배제하지 않는다. |

[progress-db.spec.ts](../../health-note/tests/progress-db.spec.ts)를 읽어 저장 대기 중 비활성화·실패 후 재시도·해제 실패·다른 브라우저와 병합·저장 중 날짜 변경 사례를 확인했다. 기존 테스트는 대기 중 잠금을 기대한다. 성공 응답을 지연시켜 즉시 표시나 다른 운동의 조작 가능 여부를 확인하는 성능 검증은 별도로 필요하다. 이번 조사에서 테스트 실행·브라우저 재현·실기기 측정은 하지 않았으며, 테스트 통과나 운영 지연 시간을 주장하지 않는다.

## 추천 해결 방향과 절충

추천: 완료 기록을 사용자·날짜·루틴·운동 단위로 낙관적으로 캐시에 반영하여 체크와 진행률을 즉시 바꾸고, 저장 실패 시 해당 항목을 되돌리고 안내한다. 저장 잠금도 해당 운동에 한정하여 다른 운동은 계속 조작할 수 있게 한다. 같은 운동의 저장 중 재입력은 잠가 요청 역전 처리를 늘리지 않는 방향을 우선 검토한다.

서로 다른 운동 요청이 겹칠 수 있으므로 날짜 전체 스냅샷을 그대로 복원하면 다른 성공 기록을 지울 수 있다. 실패 항목만 복원하고, 진행 중인 다른 저장을 재조회 결과가 덮지 않게 조정해야 한다. 계정·날짜가 바뀐 뒤 이전 요청이 새 캐시에 반영되지 않도록 키를 고정해야 한다. 영향 범위는 홈의 입력 잠금과 완료 mutation의 캐시 관리이며, DB 계약이나 네이티브 브리지를 바꿀 근거는 아직 없다.

더 작은 대안: 저장 성공 직후 해당 날짜 캐시의 항목을 갱신해 후속 GET을 화면 반영의 필수 대기에서 제거한다. 실패 처리는 단순하지만 첫 저장 요청을 기다리는 지연은 남는다. 저장 중 표시만 추가하면 대기 원인은 유지되므로 반응 속도 개선과는 구분한다.

## 실제 수정

- 홈에서 저장 중인 변경을 날짜·루틴·운동별로 조회 결과 위에 적용하여 체크와 진행률을 즉시 표시한다. 같은 항목만 잠그고 다른 운동은 조작할 수 있다.
- 실패 시 해당 임시 변경만 제거하여 서버 조회 상태로 돌아간다. 캐시 전체 스냅샷 복원은 사용하지 않는다.
- 성공 시 요청 시점의 사용자·날짜 캐시에 해당 항목만 반영하고 재조회한다. 기존 조회를 취소하여 이전 응답의 덮어쓰기를 방지한다. 날짜가 바뀌면 이전 날짜의 임시 변경은 새 날짜에 표시하지 않는다.
- 제안과의 차이: 캐시 자체를 낙관적으로 변경하는 대신 화면의 저장 중 변경을 겹쳐 표시한다. 따라서 실패 복원에서 다른 요청의 기록을 지울 위험과 스냅샷 관리가 줄어든다.
- 네이티브 앱·API·DB 계약 변경 없음. 수정·테스트·이슈 및 아키텍처 문서를 커밋 `4c6af1f`에 포함했다. 배포 미실행.
- 실기기에서 실제 앱의 체감 반응은 미확인이다.

### 저장 중 체크박스 색상 유지

- 낙관적 체크 직후 `disabled`가 적용되면서 브라우저 기본 체크박스가 회색으로 보이고, 저장 종료 후 초록색으로 바뀐다는 후속 제보가 있었다. 기본 비활성 렌더링이 원인으로 추정되며 실기기 직접 재현은 미실행이다.
- 사용자 요청으로 기본 모양을 `appearance: none`으로 제거하고 홈 체크박스의 테두리·배경·체크 표시를 CSS로 그린다. 네이티브 checkbox와 `disabled`는 유지하여 입력 차단과 체크 의미는 보존한다. 저장 중 별도 색상 변화는 주지 않는다.
- 모의 API 응답 대기 중 비활성 체크박스의 초록색 배경과 저장 후 활성 상태의 동일한 배경색을 검사했다. 기존 홈·완료 기록 브라우저 테스트 10개, lint·typecheck·변경 파일 포맷 검사 통과. 모바일 폭 대표 캡처에서 체크 표시도 확인했다.
- Android WebView 실기기 결과는 미확인. 이번 스타일 변경은 커밋 미작성·배포 미실행이다.
