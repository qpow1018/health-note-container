# Health Note

- React 19 + TypeScript + Vite 모바일 웹 프로젝트이며 npm과 package-lock.json을 사용한다.
- 구체적인 기능·화면 변경의 기획 상담, 빠진 결정 검토, 구현 지시 정리에는 [planning-health-note-changes](.agents/skills/planning-health-note-changes/SKILL.md)를 적용한다. 기획 대화만으로 제품 코드를 수정하지 않는다.
- React UI·feature 로직·TanStack Query·SCSS 작성·수정·리뷰에는 [following-health-note-frontend-style](.agents/skills/following-health-note-frontend-style/SKILL.md)을 적용한다.
- API·Supabase 인증 인프라·DB 계약·RLS·마이그레이션·환경 변수 작성·수정·리뷰에는 [following-health-note-backend-boundaries](.agents/skills/following-health-note-backend-boundaries/SKILL.md)을 적용한다. 두 영역에 걸친 작업은 각 책임에 해당하는 지침을 함께 적용한다.
- Google 로그인 후 운동·루틴·날짜별 완료 기록을 계정별 Supabase DB에 저장한다. 로컬 개발은 Docker Supabase, 운영은 클라우드 Supabase를 사용한다. 네이티브 연동은 해당 구현 요청에 맞춰 추가한다.
- 새 기능을 위한 빈 폴더, 미사용 옵션, 추상화를 미리 만들지 않는다.

## 프로젝트 문서

- 구조·책임·데이터 흐름을 다루는 작업은 [아키텍처](docs/architecture.md), 동작 정책을 다루는 작업은 [동작 결정](docs/behavior-decisions.md)의 관련 항목을 확인한다. 실행·환경·검증 명령은 [README](README.md)를 참고한다.
- 문서는 탐색의 출발점으로 사용하고 관련 코드·테스트와 대조한다. 내용이 다르면 최신 근거를 확인하며, 현재 구현을 사용자 합의나 영구적인 제약으로 간주하지 않는다.
- 요청 범위에서 구조나 동작 정책을 변경하면 관련 문서도 갱신한다. 코드의 세부 내용을 반복하기보다 책임 경계·선택 이유·절충을 기록하고 코드·테스트를 연결한다. 스타일 지침은 스킬에, 구체적인 기능 정책과 현재 구현 설명은 문서에 둔다.

## 코드 작성 전 책임과 위치 판단

- 관련된 기존 구현을 확인하고, 각 파일이 담당하는 책임을 파악한다.
- 새 코드가 어느 책임에 속하는지 판단한 뒤 작성 위치를 정한다. 코드가 짧거나 사용처가 하나라는 이유만으로 위치를 결정하지 않는다.
- 기존 구조와 다른 방식을 선택한다면, 그 이유와 이점을 설명한다.
- 단순히 기존 패턴을 따르기 위해 불필요한 컴포넌트나 추상화를 만들지는 않는다.
- 기존 구조의 역할 설명과 현재 요구에 필요한지에 대한 평가를 구분한다. 추상화·옵션·조건문은 제거했을 때 현재 필요한 어떤 동작이 깨지는지 확인하고, 기존에 있다는 사실만으로 유지 필요성을 정당화하지 않는다.
- 기존 동작과 그 근거를 확인한다. 요청 범위 밖의 동작은 유지하고, 동작 변경이 포함된 경우 합의한 요구사항에 맞춰 수정·검증한다.
- 작성 전에 책임과 위치를 결정한 근거를 짧게 공유한다. 별도의 승인 단계로 만들지는 않는다.

## 구조의 책임

- `src/api/<domain>/`: 서버 요청·응답 변환과 API·DB 경계 타입. 완료 기록 API는 `routine` 도메인에 포함한다.
- `src/queries/`: 도메인별 조회·mutation 훅, Query 키·캐시 갱신·재조회 설정.
- `src/features/<domain>/`, `src/pages/<domain>/`: 폼·일정 계산·URL 해석·조회 정책 선택·오류 안내·화면 이동.
- `src/lib/supabase.ts`, `src/lib/auth/`: 공통 Supabase 클라이언트와 현재 사용자 정보.
- `src/lib/query/`: 공유 QueryClient와 QueryProvider. 인증 사용자 변경 시에도 Provider와 동일한 인스턴스의 캐시를 초기화한다.
- API는 queries·feature·Query 캐시를 참조하지 않는다. queries는 feature·page를 참조하지 않고 서버 상태 관리에 집중한다. 자세한 배치·동작 규칙은 각 스킬을 따른다.

## 구현 작업의 스킬 적용

- 기능 구현·제품 코드 수정 요청에는 아래 두 스킬을 읽고 해당 단계에서 자동 적용한다. 별도의 호출이나 승인을 기다리지 않는다.
  - [review-feature-implementation](/Users/choewonjin/.codex/skills/review-feature-implementation/SKILL.md)
  - [test-feature-behavior](/Users/choewonjin/.codex/skills/test-feature-behavior/SKILL.md)
- 작성 전: 기존 구조와 책임을 확인하고, 사용자 합의·요구사항을 근거로 기대 동작과 검증 방법을 정한다.
- 작성 후: review-feature-implementation으로 요구사항 반영, 책임과 위치, 단순성, 불필요한 변경을 검토한다. 이어서 test-feature-behavior로 변경에 맞는 최소한의 의미 있는 검증을 선택하고 실행한다.
- 구현 중 요청 범위 안에서 만든 결함은 수정하고 다시 검증한다. 테스트만 요청받았거나 요청 범위 밖의 결함을 발견한 경우에는 제품 코드를 임의 수정하지 않고 보고한다.
- 완료 시 변경 이유, 검토 결과, 검증 결과와 미확인 범위를 작업 규모에 맞게 간결하게 설명한다. 스킬 적용을 이유로 매번 테스트 파일을 추가하거나 긴 보고서를 작성하지 않는다.
- 설명·리뷰만 요청한 경우에는 해당 스킬의 적용 조건에 따라 검토하며, 테스트를 자동 실행하지 않는다. 테스트만 요청한 경우에는 test-feature-behavior를 적용한다.
- 계획·논의·문서만 변경하는 작업에는 위 구현·검증 절차를 일괄 적용하지 않는다.
- 커밋 요청에는 스테이징할 최종 diff를 검토하고, 기존 검증 결과가 현재 코드에도 유효한지 확인한다. 이후 변경이나 검증 공백이 있을 때만 필요한 검사를 추가하며 E2E를 일괄 실행하지 않는다.

## 독립적인 판단과 의견 수정

- 사용자가 반박하거나 대안을 제시하면, 기존 의견과 같은 기준으로 검토한다.
- 사용자의 선호·목표·제약과 사실·기술적 주장을 구분한다. 선호는 선택에 반영하고, 사실·기술적 주장은 근거로 평가한다.
- 동의하기 위해 기존 판단을 바꾸거나, 독립성을 보이기 위해 억지로 반박하지 않는다.
- 의견을 바꿀 때는 어떤 새로운 근거나 조건 때문에 바뀌었는지 설명한다.
- 일부만 타당하면 동의하는 부분과 여전히 이견이 있는 부분을 구분한다.
- 기존 의견이 더 적절하다고 판단하면 이유와 단점을 함께 설명한다.
- 판단할 근거가 부족하면 불확실성을 밝히고, 필요한 확인 방법을 제시한다.
- 최종 선택은 사용자가 하되, 선택을 따르는 것과 그 선택이 더 낫다고 평가하는 것을 혼동하지 않는다.

## 검증

- 코드 변경: npm run lint, npm run typecheck.
- 환경·의존성·빌드 설정 변경: npm run build도 실행한다.
- 화면·인터랙션 변경은 PC의 모바일 폭에서 확인한다. 터치·키보드·WebView 등 기기 차이가 중요한 변경은 관련 주요 흐름을 Android에서도 확인한다.
- 화면 캡처는 변경한 UI의 대표 화면을 우선 확인하고, 다른 레이아웃·상태의 검증이나 문제 확인에 필요한 경우에만 추가한다. 모든 화면을 관성적으로 캡처하거나 변경 없이 같은 화면을 반복해서 읽지 않는다.
- 로직만 변경한 작업은 화면 배치에 영향을 주거나 화면 확인이 필요한 문제가 없는 한 캡처를 생략한다. 캡처 수를 줄이더라도 필요한 인터랙션·실패 동작 검증은 유지한다.
- API·저장·계산 로직은 변경에 관련된 정상·실패 시나리오를 선택하고, 충돌 정책이 있는 경우 관련 충돌 동작도 확인한다. 기존 테스트를 우선 활용하되 단위·통합·브라우저 테스트 중 변경을 검증하는 가장 작은 적절한 수단을 선택한다. 실제 DB 정책·제약을 변경하면 실행 중인 로컬 Supabase에서 `npm run db:test`도 실행한다.
- 모의 API 기반 브라우저 테스트는 실제 Google 인증이나 운영 RLS 검증과 구분한다. 문서·스킬만 변경한 작업은 링크·설정·포맷 검증을 수행하며 앱 테스트를 일괄 실행하지 않는다.
- 검증하지 못한 항목과 이유를 명시한다.
