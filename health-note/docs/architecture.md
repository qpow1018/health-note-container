# 아키텍처

현재 코드의 책임과 주요 데이터 흐름을 설명한다. 작성 규칙은 [AGENTS.md](../AGENTS.md), 제품 동작 정책은 [제품 동작 정책](./behavior-decisions.md), 실행·환경·검증 명령은 [README](../README.md)를 참고한다.

## 앱과 인증

React 19·TypeScript·Vite 기반 모바일 웹앱이며 React Router와 SCSS Modules를 사용한다.

- [App.tsx](../src/app/App.tsx): 공유 QueryProvider, BrowserRouter, 인증 경계와 라우트를 조립한다. 홈·플랜·운동 관리·마이페이지에는 하단 내비게이션을 제공한다. 운동 관리는 `/exercise`의 루틴 목록을 기본으로 하며, `?tab=exercises`에서 등록한 운동을 관리한다. 루틴 목록 진입점도 `/exercise`로 통합한다.
- [AuthBoundary.tsx](../src/app/AuthBoundary.tsx): 세션 복원 중에는 대기 화면, 비로그인 상태에서는 로그인 화면을 표시한다. 로그인한 사용자 ID를 key로 하위 화면을 재마운트하고 AuthUserContext로 원본 사용자 정보와 표시용 닉네임을 함께 전달한다. 표시용 닉네임은 저장된 값이 비어 있지 않은 문자열이면 사용하고, 아니면 `회원`으로 계산하며 계정에 별도로 저장하지 않는다. 마이페이지는 이 정보를 표시하며 별도 인증 구독이나 사용자 조회를 만들지 않는다.
- [useAuthSession.ts](../src/features/auth/useAuthSession.ts): 세션 복원과 인증 이벤트 구독을 처리한다. 사용자 변경 시 현재 사용자 정보를 갱신하고 공유 QueryClient의 캐시를 비운다.
- [QueryProvider.tsx](../src/lib/query/QueryProvider.tsx): 캐시 초기화에 사용하는 것과 동일한 QueryClient를 제공한다.

닉네임 편집 팝업은 `features/profile/NicknameForm.tsx`, 저장 요청은 `api/auth`가 담당한다. 마이페이지가 메뉴 진입과 열림 상태를, 폼이 공통 Modal을 사용한 입력·검증·저장·취소를 담당한다. 팝업을 닫으면 초안을 버리고, 저장 중에는 취소와 Escape 닫기를 막는다. Supabase Auth의 `user_metadata.nickname`을 사용하고 `USER_UPDATED` 이벤트를 기존 세션 구독에서 받아 사용자 정보에 반영한다. 별도 프로필 테이블이나 Query 캐시는 추가하지 않는다.

현재 인증 구현은 사용자별 재마운트와 캐시 초기화를 함께 사용해 이전 계정의 데이터·편집 상태가 이어지지 않도록 한다. 보안 경계는 클라이언트의 화면 차단이 아니라 DB의 사용자 소유 RLS다.

## 책임과 위치

| 위치                     | 책임                                                  |
| ------------------------ | ----------------------------------------------------- |
| `src/app/`               | Provider·인증 경계·레이아웃·라우트 조립               |
| `src/pages/<domain>/`    | URL 해석·화면 조립·사용자 안내·저장 후 이동           |
| `src/features/<domain>/` | 폼·검증·일정 계산·기능별 화면 로직                    |
| `src/queries/`           | 조회·mutation 훅·Query 키·캐시 갱신·재조회 설정       |
| `src/api/<domain>/`      | 서버 요청·응답 변환·API와 DB 경계 타입                |
| `src/lib/`               | Supabase 클라이언트·현재 사용자 정보·공유 QueryClient |
| `src/components/common/` | 도메인과 무관한 공용 UI                               |
| `src/styles/`            | 폰트·테마·공통 토큰·전역 스타일                       |
| `tests/`                 | Playwright 테스트와 모의 API                          |
| `supabase/migrations/`   | DB 테이블·RLS·제약·RPC의 버전 관리                    |

API는 Query 캐시나 화면에 의존하지 않고, queries는 feature·page·라우터에 의존하지 않는다. 기존 완료 기록 테이블은 보존하며 현재 웹에서의 기록 조회·변경 흐름은 제거했다. `supabase/schema.sql`은 미적용 초안이므로 실제 스키마 판단에는 migrations를 사용한다.

## 조회와 저장 흐름

조회는 `page/feature → query 훅 → API → Supabase`로 진행한다. Query 훅은 도메인 객체를 default export하며, 화면은 `exerciseQuery.useGetExercises()`, `routineQuery.useGetRoutines()`처럼 호출한다. API는 DB의 snake_case를 앱의 camelCase로 변환하고, Query는 서버 상태를 관리하며, 화면은 로딩·오류·빈 상태를 표시한다.

저장은 화면에서 요청 값을 준비해 mutation에 전달한다. API 결과에 따라 Query 캐시를 갱신하고, 화면에서 실패 안내나 성공 후 이동을 처리한다. 폼 초안·미저장 정렬은 서버 캐시와 별도의 편집 상태다.

운동 목록·상세·수정은 [exerciseQuery.ts](../src/queries/exerciseQuery.ts)의 사용자별 목록 캐시를 공유한다. 상세·수정 화면은 이 목록에서 URL의 ID에 해당하는 운동을 선택한다. 별도 상세 API는 사용하지 않는다. 루틴도 [routineQuery.ts](../src/queries/routineQuery.ts)의 사용자별 목록 캐시를 목록·상세·수정·정렬·홈에서 공유한다. 화면별 조회 래퍼나 라우터 키로 나눈 캐시는 두지 않는다.

루틴 수정은 편집 시작 시 원본을 보관해 재조회 이후에도 버전 충돌 검사의 기준으로 사용한다. 폼 초안은 재조회 실패·복구로 초기화하지 않는다. 기존 데이터가 있으면 오류 안내와 함께 유지한다.

## 캐시 정책의 현재 구현

[queryClient.ts](../src/lib/query/queryClient.ts)의 공통 설정은 `staleTime` 1분, 조회 `retry: false`다. `gcTime`은 라이브러리 기본값인 5분이며, 포커스·재연결 재조회도 기본값을 사용한다. 1분은 자동 갱신 주기가 아니라 데이터를 최신 상태로 간주하는 시간이다. 주기적 폴링이나 실시간 구독을 뜻하지 않는다.

- 운동·루틴 mutation은 성공 시 관련 목록을 무효화하고, 사용 중인 Query를 기본 동작으로 재조회한다. 충돌 결과는 성공으로 처리하지 않는다. 목록 정렬은 드롭 시 저장하며, 드래그·응답 대기 동안만 임시 순서를 보관한다. 실패하면 복구하고 충돌하면 최신 목록을 조회한다.

이 설정은 현재 구현 설명이며 모든 도메인에 강제할 규칙은 아니다.

## 검증 경계

브라우저 테스트는 인증과 데이터 API를 모의 응답으로 제어한다. fixture의 localStorage는 테스트 데이터 저장 수단이며 제품의 저장소가 아니다. 실제 데이터는 계정별 Supabase DB에 저장한다.

DB 제약·RLS·RPC는 로컬 Supabase의 DB 테스트로 확인한다. 모의 API 테스트는 실제 Google 인증·운영 DB·Android 실기기 동작의 증거가 아니다. 실행 방법과 환경은 README를 참고한다.

## Android 걸음 카드

홈은 [StepCard](../src/features/steps/StepCard.tsx)를 닉네임 아래에 조립한다. Android 네이티브 모듈의 응답을 받은 경우에만 표시하며 일반 브라우저·iOS·이전 APK에는 표시하지 않는다. 센서 측정과 기기 저장은 앱이 담당하고 권한 요청과 기본 자동 기록 시작은 앱이 담당하고 웹은 상태 조회·오늘 기록 초기화 요청과 결과 표시만 담당한다. 켜기·끄기 버튼은 제공하지 않는다. 서버 상태가 아니므로 Query 캐시나 API 계층을 추가하지 않는다.

홈이 보이는 동안 5초마다 최신 상태를 조회하고 문서가 다시 보일 때도 갱신한다. 날짜가 다른 이전 응답의 걸음수는 오늘 값으로 표시하지 않는다. 계정별 운동·루틴과 달리 걸음 기록은 휴대폰에 귀속되며 카드에 기기 내부 저장을 안내한다. 메시지 계약과 서비스·날짜 경계는 [앱 아키텍처](../../health-note-app/docs/architecture.md#android-자동-걸음-기록)를 참고한다.

개발 서버의 일반 브라우저에서는 `import.meta.env.DEV`가 참이고 WebView 연결 객체가 없을 때만 오늘 4,567걸음의 미리보기를 자동 표시한다. 앱에서는 개발 서버에 연결해도 실제 네이티브 응답을 사용한다. 미리보기는 컴포넌트 메모리에만 존재하고 초기화 후 새로고침하면 샘플로 돌아오며, 운영 빌드에서는 비활성화된다.

## 오늘 활동 화면

홈 StepCard는 오늘 걸음수·활동 시간·실측 거리를 요약하고 `/activity` 상세 화면으로 연결한다. `useActivitySnapshot`은 두 화면에서 네이티브 이벤트 구독·화면이 보일 때의 5초 조회를 소유한다. 서버 데이터가 아니므로 API·Query 캐시를 만들지 않는다. 날짜가 다른 응답은 오늘 기록으로 표시하지 않는다.

상세는 오늘 요약과 이동 중 평균 속도, 걸음수/활동 시간/거리 전환 그래프, 시간대 선택값과 3분 이상 활동 목록을 제공한다. 그래프는 24시간을 좌우로 스크롤해 선택하며 버튼으로 키보드 조작도 가능하다. 활동 시간은 걸음 간격으로 계산한 값이라는 점과 위치 확보 구간만 실측한다는 점을 안내한다. 권한·GPS 꺼짐·측정 실패는 위치 상태로 따로 표시하고 기존 걸음 기록을 차단하지 않는다.

오늘 초기화는 오늘 총걸음수·시간별 집계·활동 목록에 함께 적용된다. 개발 일반 브라우저는 동일 계약의 샘플 데이터로 요약·그래프·초기화를 미리 볼 수 있으며 실제 저장은 하지 않는다. 운영 빌드는 네이티브 응답을 기다린다. UI는 `activity.ts`에서 응답 구조와 숫자 범위를 검증하고 구형 snapshot에는 활동 집계를 강제로 만들어 넣지 않는다.

## 운동이 캐릭터

`/playground`는 바텀 메뉴의 운동장에서 진입한다. `pages/playground/PlaygroundPage.tsx`는 헤더와 본문 여백을 조립하고 `CharacterPlayground`를 표시한다. 기존 `/character` 라우트와 실험 탭·미리보기 페이지는 제거했다. 캐릭터 실험은 이후 홈에서 이어갈 예정이며 이번 변경에서는 홈에 실험 UI를 추가하지 않았다. 캐릭터는 SVG로 표현하며, 이미지·3D·부위 분리 후보의 전용 구현과 에셋은 제거했다.

`assets/sprout/SproutStage1Front.tsx`를 1단계 정면의 기준 외형으로 관리한다. 몸·잎·얼굴·팔·발의 경로·색·비율과 부위 이름만 정의하며 동작·화면 상태를 참조하지 않는다. 기존 1단계 몸 윤곽 경로를 클리핑으로 분리해 기본 외형을 유지하면서 팔을 움직인다. `assets/sprout/index.ts`에는 실제 존재하는 단계·방향의 외형과 viewBox만 등록한다. 현재 등록은 1단계 정면뿐이며, 미제작 방향을 정면으로 대신 표시하지 않는다.

`SproutCharacter.tsx`는 등록된 외형을 선택하고 공통 동작 스타일을 적용한다. `SproutCharacter.module.scss`가 대기·걷기·운동·인사 반응과 재생 상태·동작 줄이기를 담당한다. 화면별로 새싹을 다시 그리지 않는다. `InteractiveCharacter.tsx`는 이후 홈 실험에 사용할 누름·점프 상호작용 코드로 보존하며 현재 화면에는 연결하지 않는다. `Character.tsx`는 종류에 따라 외형을 선택하며, 1단계 새싹을 `SproutCharacter`로 연결하며 `assets/mochi/MochiStage1Front.tsx`의 찹쌀떡 외형을 표시한다. 찹쌀떡 에셋은 경로·색·부위 이름만 정의하고, `Character.module.scss`에서 부위 이름으로 호흡·눈 깜빡임·인사 반응을 적용한다. 새싹 2~6단계 성장 초안은 제거했다.

현재 운동장은 기본 새싹만 표시하며 단계 선택 UI는 제공하지 않는다. 레벨·경험치에는 연결하지 않는다. 찹쌀떡은 코드만 보존하고 후보 선택 UI는 제공하지 않는다. 화면 밖·숨긴 탭에서는 움직임을 멈추며 동작 줄이기 설정에서는 반복 움직임과 점프를 끄고 투명도로 누름을 표현한다. 관련 검증: [운동장 진입](../tests/playground-navigation.spec.ts), [기준 외형 공유](../tests/character-assets.spec.ts), [닉네임 편집](../tests/my.spec.ts).

### SVG 운동장

`CharacterPlayground`는 고정 구도의 운동장 배경과 운동이 5마리의 배치·행동·재생 상태를 담당한다. `SproutCharacter`의 동일한 1단계 정면 외형을 사용하고 행동만 지정한다. 팔·발·잎·눈·줄넘기 줄을 독립 그룹으로 움직이며 화면마다 외형을 중복 정의하지 않는다. 이미지 모드 분기와 이미지 프레임 애니메이션은 제거했다.

스트레칭·줄넘기·산책·공놀이·뛰놀기의 고정된 장면을 비교하는 시뮬레이터이며 전체 일시정지와 화면 밖·숨긴 탭 정지, 동작 줄이기를 지원한다. 실제 물리·경로 탐색·보유 개체·완료 기록·서버 저장과 연결하지 않는다. 관련 검증: [SVG 운동장](../tests/character-playground.spec.ts).

## 운동 관리 통합

운동과 루틴의 페이지는 `pages/exercise/`, 화면 기능은 `features/exercise/`에서 관리한다. 루틴 페이지도 같은 폴더에 두며 파일명으로 구분한다. API와 Query는 기존 exercise·routine 도메인 구분을 유지한다. `components/common/tabs/Tabs`는 항목·주소·선택 상태를 받아 링크 탭을 표시하고, `pages/exercise/ExercisePage`는 URL에 따른 선택 상태, 공통 헤더·탭과 본문 여백을 담당한다. `features/exercise/ExerciseList`와 `RoutineList`는 각 목록의 조회·로딩·오류·빈 상태·항목 표시를 담당한다. 운동 관리 내비게이션은 루틴과 등록한 운동 목록 사이를 이동하며, 운동 상세·생성·정렬에서 목록으로 돌아오면 등록한 운동 탭을 표시한다.

루틴은 일정 없는 운동 묶음으로 전환했다. 플랜 연결 전까지 홈의 기존 오늘 루틴·완료 조작은 제거했다. `save_routine_bundle` RPC는 기존 원자적 저장·RLS·버전 충돌 검사를 재사용하고 일정 입력을 받지 않는다. DB의 과거 일정·활성화 열과 완료 기록은 보존한다. 모든 feature의 작성·배치 기준은 [프론트엔드 스킬](../.agents/skills/following-health-note-frontend-style/SKILL.md)을 따른다. 날짜 갱신은 도메인과 무관한 `hooks/useTodayDate`를 홈·활동 화면이 사용한다.

운동 목록은 상단에 운동 추가 링크를 제공하고, 상세 링크와 별도 드래그 핸들을 각 행에 표시한다. 드롭 시 기존 순서 충돌 검사 API로 즉시 저장하며 저장 중에는 핸들을 잠근다. 실패하면 임시 순서를 제거하고, 충돌하면 최신 목록을 재조회한다. 드래그 중의 목록과 저장 응답 대기 중의 순서만 로컬 상태로 보관하며 평소에는 Query 목록을 표시한다. 별도 운동·루틴 정렬 페이지는 제거했다. 루틴 목록도 같은 방식으로 추가·상세 진입·즉시 정렬을 제공한다.

## 플랜 설정 화면

생성 페이지는 `PlanCreatePage.module.scss`에서 좌우·하단 여백과 safe area를 관리한다. 폼은 운동·루틴 폼과 동일하게 시작 간격 32px, 입력 그룹 간격 24px을 사용하고 공통 Button을 하단에 고정한다. 본문에는 고정 버튼에 가리지 않도록 하단 공간을 확보한다.

하단 메뉴의 `/plan`은 진행 중인 플랜을 조회한다. 플랜이 없으면 안내와 생성 진입을 제공하고, 있으면 저장한 기간·주간 운동표·경험치 배분 기준을 표시한다. 루틴 목록 자체를 별도로 조회하지 않고 플랜 조회의 연결 정보에서 이름을 받는다. 루틴 유무·로딩·오류는 생성 페이지 `/plan/new`에서 처리한다. `/plan/new`은 헤더와 조회 상태를 조립하고, `features/plan/PlanForm.tsx`가 기간·요일별 배정 초안과 요약을 관리한다. 루틴 조회는 기존 `routineQuery.useGetRoutines()`를 재사용한다. `PlanForm`은 편집 중인 요일·배정과 공통 BottomSheet의 열림 상태를 제어하고, `PlanRoutinePicker`는 공통 Radio로 루틴 선택 항목을 제공한다. 선택창이 열릴 때만 마운트해 기존 운동 조회 훅으로 포함 운동을 조회하며, 선택 시 부모의 배정을 갱신하고 닫는다. `utils/planSchedule.ts`는 시작일을 포함한 기간의 운동일 수와 고정 성장 목표 9,000 XP 기준 하루 몫을 계산한다. 운동일이 없으면 하루 몫은 null이며 화면에서 선택을 안내한다. 반올림은 미리보기 표시에만 적용한다.

루틴 생성은 진입 경로 구분 없이 `/routine/new`를 사용한다. 저장 성공 후 `navigate(-1)`로 진입했던 화면으로 돌아오고, 헤더는 공통 뒤로가기 동작을 사용한다. 플랜의 미저장 입력은 화면 내부 초안이며 이동·새로고침 시 초기화한다. 저장에 성공한 플랜은 계정별 DB에서 다시 조회한다. 관련 검증: [플랜 설정](../tests/plan.spec.ts), [플랜 저장](../tests/plan-save.spec.ts).

### 플랜 저장과 조회

`api/plan`은 `create_plan` RPC와 진행 중 플랜 조회·응답 변환을 담당하고, `queries/planQuery.ts`는 사용자별 플랜 캐시와 저장 후 무효화를 관리한다. 생성 페이지는 먼저 진행 중 플랜을 확인하고, 없을 때 루틴 조회와 폼을 표시한다. 플랜 확인 또는 루틴 재조회가 실패해도 이미 표시한 초안은 유지한다. 폼은 입력 검증·저장 중 중복 제출 차단을, 페이지는 저장 실패 안내·성공 후 이동을 담당한다.

`plans`는 시작일·기기 시간대·기간·상태·고정 목표 XP·최초 운동일 수를, `plan_weekdays`는 요일별 루틴 연결을 보존한다. 하루 XP는 반올림한 값으로 저장하지 않는다. 루틴 자체를 복제하지 않고 ID로 연결하므로 루틴 이름·구성 변경이 반영된다. 루틴 수정 성공 시 플랜 조회 캐시도 무효화한다.

서버는 해당 시간대의 오늘인지, 지원 기간인지, 최소 하루가 배정됐는지, 선택한 루틴이 현재 사용자 소유인지 확인하고 한 트랜잭션으로 저장한다. 요청 ID는 생성 화면이 유지되는 동안 재사용해 응답 유실 후 재시도가 중복 저장되지 않게 한다. 계정별 잠금과 진행 중 상태에 대한 유일 인덱스가 동시 생성을 제한한다. 노출 테이블의 RLS·열별 권한과 지연 제약은 RPC를 거치지 않은 쓰기에도 소유권·배분 기준을 검사한다.

진행 중인 플랜에서 사용하는 루틴은 DB에서 삭제를 거부하고 API가 `in-use`로 변환해 화면에 안내한다. 루틴에 연결된 운동의 기존 삭제 제한은 유지한다. 종료 플랜의 연결은 루틴 삭제 시 참조만 비우며 플랜 자체는 남긴다. 종료·중단을 실행하는 API·화면과 운동 완료·XP 지급·날짜별 구성 기록은 아직 구현하지 않았다.

DB 계약: [플랜 마이그레이션](../supabase/migrations/20261021063214_create_plans.sql). 검증: [플랜 DB 테스트](../supabase/tests/plans.test.sql).

## 플랜 첫 화면 미리보기

`PlanPage`는 플랜 조회·로딩·오류 처리와 Intro/진행 중 화면 분기를 담당한다. 플랜이 있으면 헬스노트 로고 헤더 아래 `features/plan/ActivePlan`에 플랜과 오늘 날짜를 전달한다. ActivePlan은 플랜 유무를 판단하거나 Intro를 렌더링하지 않는다. PlanPage의 플랜 ID·날짜 key로 완료 체크의 초기화 범위를 정한다. 플랜 요약 → 작은 운동이 영역 → 오늘 운동 순서로 배치한다. 기존 새싹 에셋을 재사용하며 성장 단계별 외형은 추가하지 않는다.

진행 중 플랜·현재 루틴·운동은 기존 Query를 통해 조회한다. 요약은 `/plan/detail`의 읽기 전용 상세로 연결하고, 오늘 배정이 없으면 휴식 안내를 표시한다. 플랜이 없으면 `features/plan/PlanIntro`에서 소개와 운동 만들기·루틴 만들기·플랜 만들기 순서를 표시한다. 기존 Query로 운동·루틴 등록 여부를 조회해 완료를 표시하고 다음 단계를 강조한다. 조회 실패는 미완료로 표시하지 않는다. 단계 링크는 기존 생성 화면을 사용하며 저장 후 이동 정책은 유지한다. 조회 실패는 빈 플랜으로 처리하지 않는다.

완료 체크와 표시 XP·레벨은 미리보기용 로컬 상태다. 초기 XP는 0이며 오늘 체크 비율에 하루 몫을 적용해 운동이의 성장을 보여준다. 서버 기록·기존 완료 데이터는 변경하지 않고 새로고침·날짜 변경 시 초기화한다. 실제 XP 지급·날짜별 구성 보존·성장 완료 처리와 구분하며 화면에 미저장 미리보기임을 표시한다. 관련 검증: [플랜 첫 화면 미리보기](../tests/home.spec.ts).

첫 진입 `/`는 인증 확인 후 `/plan`으로 replace 이동한다. 로그인 복귀 주소 `/`는 네이티브 인증 계약을 위해 유지한다. 하단 메뉴는 플랜·운동·운동장·마이이며 별도 홈 화면은 두지 않는다. 플랜이 없으면 `/plan/new`로 연결한다.

`PlanDetailPage`는 진행 중 플랜 Query를 재사용해 기간·시작일·기간 기준 종료일·주간 운동표·성장 기준을 보여준다. 상세는 하단 메뉴 밖의 독립 화면이고 헤더 뒤로가기의 직접 진입 fallback은 `/plan`이다. 플랜 없음과 조회 실패를 구분한다. 일정 수정·중단 기능은 아직 제공하지 않는다.

플랜 상세 UI는 생성 화면의 시각 규칙을 참고하되 별도 컴포넌트·스타일로 관리한다. 일정 요약 → 읽기 전용 주간 운동표 → 성장 기준 순서로 배치하며, 요일은 36px 박스로 표시한다. 선택 중인 폼과 확정된 상세의 역할 차이 때문에 공용 요약 컴포넌트는 추출하지 않았다.
