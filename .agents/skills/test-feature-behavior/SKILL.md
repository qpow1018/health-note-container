# 기능 테스트

변경 내용과 요구사항에 맞는 가장 작은 의미 있는 검증을 선택한다. 단위·통합·E2E를 매번 모두 만들거나 실행하지 않는다.

## 범위

- "테스트해줘"는 지정한 기능의 테스트 작성·실행·테스트 코드 수정 요청으로 해석한다. 계획이나 설명만 요청하면 실행하지 않는다.
- 프로젝트 지침에 따른 구현 중 검증에도 적용한다. 구현 요청 범위 안에서 이번 변경이 만든 결함은 수정하고 관련 검증을 다시 수행한다. 독립적인 테스트 요청과 구현 중 검증의 권한을 구분한다.
- 먼저 AGENTS.md, 관련 프로젝트 스킬, Git 상태, 검사 명령, 기존 테스트·설정을 확인한다. 사용자 작업을 되돌리거나 광범위하게 포맷팅하지 않는다.
- 명시된 기능·경로·커밋을 기준으로 범위를 좁힌다. 없으면 현재 변경을 우선하며 대상이 불명확하면 필요한 정보만 질문한다.
- 프로젝트의 린터와 TypeScript 명령을 사용한다. ESLint·Oxlint 중 하나를 강제하거나 기존 도구를 교체하지 않는다. 포맷터는 필수가 아니며 이미 있다면 해당 규칙을 따른다.
- 필요한 테스트 도구가 없다면 최소한의 도입안을 설명한 뒤 요청된 테스트에 직접 필요한 개발 의존성과 설정만 추가할 수 있다. 설치 권한은 환경 정책을 따른다. 관련 lockfile을 함께 관리한다.
- 독립적인 테스트 요청에서는 제품 코드·기능·공개 API를 임의 변경하지 않는다. 테스트를 위해 제품 코드를 재설계하거나 검증을 export하지 않는다. 구조상 테스트가 어렵다면 적절한 상위 범위의 테스트나 수동 확인을 선택하고 제약을 보고한다.
- 독립적인 테스트나 구현 요청 범위 밖에서 제품 문제를 발견하면 재현 테스트가 있다면 유지하고 실패로 보고한다. 테스트 자체의 오류는 수정한다. 해결을 요청받지 않은 제품 결함 때문에 무한 재시도하지 않는다.

## 기대 결과와 근거

- 사용자 합의, 요구사항 문서, 공개 계약에서 기대 결과를 먼저 정한다. 구현을 그대로 복사해 테스트 기대값을 만들지 않는다.
- 요구사항 자료가 없으면 코드의 명백한 계약과 일반적인 데이터 보존 조건을 검사하되 기능 정책을 임의 확정하지 않는다. 중요한 모호함은 질문하고 독립적인 검증은 계속한다.
- 변경의 입력·출력, 상태, 저장/API, 화면 이동과 관련 호출부를 확인한다.
- 기존 테스트의 커버 범위와 공백을 읽고 재사용한다. 커버리지 수치나 테스트 개수 자체를 목표로 삼지 않는다.

## 테스트 선택

| 범위 | 적합한 상황                            | 주의점                                                                                 |
| ---- | -------------------------------------- | -------------------------------------------------------------------------------------- |
| 단위 | 조건이 많은 검증·계산·변환·저장 로직   | 함수별 테스트를 의무화하지 않는다. 사소한 구현 복제는 피한다.                          |
| 통합 | 화면·상태·저장/API 연결, 실패 처리     | 실제 내부 모듈을 가능한 한 함께 쓰고 외부 경계를 제어한다.                             |
| E2E  | 등록·조회·새로고침 등 핵심 사용자 흐름 | 실제 브라우저에서 사용자에게 보이는 결과를 확인한다. 모든 입력 조합을 반복하지 않는다. |

- 단위 테스트가 처리한 상세 조건을 E2E에서 모두 중복하지 않는다. 각 범위가 발견하는 실패의 차이가 있을 때 조합한다.
- 작은 앱은 E2E 중심으로 시작할 수 있다. 단위·통합 테스트는 조건 조합이나 실패 재현 비용이 낮아질 때 추가한다.
- 컴포넌트 테스트가 화면·로직 연결을 검사하면 통합 범위로 설명할 수 있다. 별도의 네 번째 테스트 계층을 강제하지 않는다.
- lint·typecheck·build는 동작 테스트와 별도 검증이다. 실행했다면 구분해 보고한다. 설정·의존성 변경에는 프로젝트 지침의 빌드 검증을 따른다.

## 작성과 실행

- 정상 흐름 외에 해당 변경에서 의미 있는 경계·실패 조건을 선택한다. 저장 기능은 기존 데이터 보존·저장 실패·손상 데이터 처리, 입력은 필수·선택 값·잘못된 값 등을 고려한다.
- 테스트는 동작과 관찰 가능한 결과에 집중한다. 함수 호출 순서, 내부 state, CSS 클래스 등에 불필요하게 결합하지 않는다.
- 외부 API는 통제된 응답으로 검사하고 실제 외부 서비스 가용성 자체를 테스트하지 않는다. 통제한 경계는 보고한다.
- 테스트마다 데이터·저장소·시간 의존성을 격리한다. 실제 사용자 localStorage, 계정, DB 데이터를 삭제하거나 덮어쓰지 않는다.
- E2E는 테스트용 브라우저 컨텍스트와 환경을 사용한다. 생성 데이터의 정리는 격리된 테스트 데이터에만 한정한다. 브라우저 조작은 환경에서 허용된 도구를 따른다.
- 고정 sleep보다 조건 대기를 사용하고, 재시도로 실패를 숨기지 않는다. 재시도는 일시적인 환경 문제라는 근거가 있을 때 제한적으로 수행한다.
- 필요한 최소 범위부터 실행한다. 새 변경·실패·미확인 문제가 없으면 같은 검증을 반복하지 않는다.
- Android 실기기 확인이 필요한 키보드·터치·센서·백그라운드 동작은 브라우저 에뮬레이션과 구분한다.
- 환경 차단은 제품 실패와 구분한다. 실행하지 못한 테스트를 통과로 처리하지 않는다.

## 실패 판단

- 제품 결함: 요구사항과 실제 결과가 다름. 코드 위치와 재현 조건, 기대/실제 결과를 보고한다.
- 테스트 결함: 잘못된 설정·locator·fixture·기대값. 요구사항 근거를 확인해 테스트를 수정한다.
- 환경 실패: 서버·의존성·권한·외부 환경 문제. 가능한 안전한 해결만 진행하고 남은 제한을 명시한다.
- 실제 버그를 숨기려고 assertion을 약화하거나 skip·mock·timeout·retry를 늘리지 않는다.

## 보고

짧게 다음을 제공한다.

- 선택한 테스트 범위와 이유, 생략한 범위의 중요한 이유.
- 검증한 요구 동작·실패 조건과 이를 확인한 수단, 실행 명령과 통과·실패·미실행 결과. 테스트 개수만 나열하거나 통과를 전체 제품 품질로 확대하지 않는다.
- 새 테스트·설정 파일의 링크. 테스트 추가·수정과 제품 코드 변경 여부를 구분한다.
- 제품 문제의 재현 조건, 기대/실제 결과, 관련 코드 위치. 구현 중 수정한 이번 변경의 결함과 아직 남은 문제를 구분한다. 독립적인 테스트 요청이나 구현 범위 밖의 제품 수정은 별도 요청으로 남긴다.
- mock으로 대체한 경계, 브라우저·실기기 미확인 등 한계.

구현 완료 보고에서는 검증 결과를 한 번만 통합하고 별도 테스트 보고서를 반복하지 않는다. 전체 구현 설명이나 코드 리뷰를 반복하지 않는다. 커밋·배포는 별도 요청이 있을 때만 진행한다.
