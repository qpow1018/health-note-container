# 구현 설명과 판단 근거

사용자가 변경된 코드 전체를 뒤지는 시간을 줄이고, 중요한 동작·설계 선택과 근거를 골라 검토하도록 돕는다. AI의 자체 검토를 사용자 검토의 대체 증거로 삼지 않는다. 설명으로 평가를 대신하거나 구현을 옹호하지 않고, 더 단순한 방법도 검토한다.

## 요청 구분

- "구현 설명해줘" 또는 기능의 구현을 이해하고 싶다는 요청에 핵심 흐름과 선택 이유를 설명한다. 요구사항 반영과 단순성·유지보수 평가도 포함한다.
- 구현 완료 전 자체 검토·수정은 [self-review-health-note-changes](../self-review-health-note-changes/SKILL.md)가 담당한다. 이 설명 스킬을 구현 후 자동 실행하거나 완료 보고의 필수 절차로 삼지 않는다.
- "코드 리뷰해줘"만 요청하면 이 스킬을 자동 적용하지 않는다. 일반 코드 리뷰로 버그·누락·위험과 수정할 부분에 집중한다.
- "결과 보고해줘"만 요청하면 이미 확보한 검토·검증 결과를 간결하게 요약한다. 이 요청만으로 검토나 검증을 다시 실행하지 않는다.
- 사용자가 이 스킬을 명시적으로 지정하거나 설명과 리뷰를 함께 요청하면 적용한다.

## 범위와 근거 확보

- 설명 요청은 기본적으로 읽기 전용이다. 설명 중 문제를 발견해도 알리는 데 그치며, 보고서 파일 생성·코드 수정·커밋은 별도 요청에 따른다.
- 현재 저장소의 AGENTS.md와 적용되는 프로젝트 스킬을 따른다. 다른 프로젝트의 구조·스타일을 강제하지 않는다.
- 설명 대상은 사용자가 명시한 기능·경로·커밋 → 현재 대화에서 구현한 대상 → 관련 Git 변경 순으로 정한다. Git 상태와 diff는 대상의 변경 범위를 확인하는 근거로 사용하며, 이미 커밋한 구현보다 무관한 미커밋 변경을 우선하지 않는다. 그래도 대상을 특정할 수 없으면 필요한 정보만 질문한다.
- 같은 기능의 진입점, 호출부, 상태, 저장/API 경계, 관련 테스트를 따라 읽는다. diff만 보고 기존 호출부와 동작을 추정하지 않는다.
- 변경 중인 파일을 되돌리거나 포맷팅하지 않는다. 설치·서버 실행·상태 변경을 수반하는 검증은 현재 권한과 사용자 요청 범위를 확인한다.
- 현재 대화, 사용자 제공 요구사항, 저장소 문서, 접근 가능한 승인 기록에서 기능의 합의를 찾는다.
- 다른 세션의 대화는 자동으로 전달되지 않는다. 없는 대화를 기억하거나 읽었다고 주장하지 않는다. 요구사항 자료가 없으면 코드에서 확인한 흐름은 설명하되 '대화 반영 확인 불가'라고 표시한다. 중요한 판단에만 필요한 설명을 요청한다.
- 문서·커밋 메시지만으로 구현 완료를 인정하지 않는다. 실행하지 않은 동작은 코드상 판단과 런타임 확인을 구분한다.

## 설명할 내용

### 이해를 돕는 설명 순서

- 기본 흐름은 사용자 행동 → 내부에서 이어지는 일 → 이해해야 할 중요한 선택 → 직접 볼 코드 순으로 잡는다. 특정 함수나 설계만 질문했다면 그 질문에서 시작한다. 이 순서를 고정된 제목이나 보고서 양식으로 만들지는 않는다.
- 사용자가 아는 구체적인 상황 하나에서 시작한다. 저장 버튼 클릭, 앱 복귀처럼 실제 진입점을 잡고 최종적으로 화면이나 데이터에 무엇이 달라지는지 먼저 짚는다. 화면이 없는 변경은 호출이나 입력·출력에서 시작한다.
- 그 상황에서 입력·상태·데이터가 어디로 전달되고 어떤 결과로 이어지는지 인과관계로 설명한다. 파일별로 끊어 나열하기보다 하나의 흐름을 끝까지 연결하고, 중요한 실패·분기는 해당 지점에 붙인다.
- 선택 이유는 문제가 생기는 상황 → 현재 처리 방식 → 효과와 제약 순으로 설명한다. 예를 들어 중복 실행 방지는 “앱 복귀와 화면 로드가 겹치면 같은 작업이 두 번 시작될 수 있어 진행 여부를 기억해 두 번째 호출을 막는다”처럼 설명한 뒤, 해당 값을 ref로 관리하는 코드를 연결한다. 실제 구현에 없는 상황이나 처리를 예시처럼 단정하지 않는다.
- 기술 용어·함수명은 동작을 설명한 뒤 실제 코드와 연결할 때 사용한다. 사용자가 익숙한 기술의 기본 개념까지 장황하게 풀지는 않는다. 코드 링크마다 그 위치에서 무엇을 확인할 수 있는지 짚는다.
- 요구사항 반영·설계 평가·검증 근거는 관련 흐름과 선택에 붙인다. 항목을 빠짐없이 나열하느라 핵심 흐름이 묻히지 않도록 한다.

### 기능과 요구사항

- 실제 사용자가 할 수 있는 동작, 미구현 범위, 실패 시 동작을 먼저 파악한다.
- 합의 항목별로 반영 / 일부 반영 / 미반영 / 확인 불가를 구분한다. 관련 경로와 동작 근거를 연결한다.
- 사용자 합의, 구현자가 선택한 정책, 리뷰어의 제안을 구분한다. 기존 코드에 있다는 이유로 사용자 합의라고 부르지 않는다.
- 요구사항 자료가 없으면 구현된 동작을 요구사항처럼 역으로 만들어내지 않는다.

### 설계와 이유

- 입력부터 검증, 상태 변경, 저장, 화면 반영까지 핵심 흐름을 평이한 말로 설명한다.
- 설명할 가치가 있는 선택만 다룬다. 모든 함수와 파일을 나열하지 않는다.
- 확인된 결정 이유와 코드에서 추론한 장점을 구분한다. 개발자의 실제 동기를 코드만으로 단정하지 않는다.
- 선택의 이점과 제약, 더 단순한 현실적인 대안이 있을 때 그 차이를 설명한다. 미래의 가상 기능만으로 복잡한 구조를 정당화하지 않는다.

### 정확성·단순성·유지보수

- 핵심 흐름에 관련된 실패 처리와 기존 데이터·사용 환경에 미치는 영향을 설명한다.
- 책임의 위치·데이터 흐름·상태와 추상화의 필요성을 평가하고, 현실적인 단순화 여지가 있으면 구체적인 대안과 차이를 설명한다. 줄 수만 줄이려고 책임을 숨기지 않는다.
- 설명 중 발견한 요구사항 누락·잘못된 동작·불필요한 복잡도를 숨기지 않는다. 취향이나 프로젝트와 무관한 유행을 결함으로 제시하지 않는다.
- 요청과 무관한 대규모 리팩터링을 권하지 않는다.

### 검증

- 타입·린트·빌드는 동작 테스트와 구분한다.
- 설명 요청에서는 테스트·린트·타입 검사·빌드 명령, 개발 서버, 브라우저·실기기 검증을 자동 실행하지 않는다. 이전 구현 요청의 검증 권한만으로 재실행하지 않는다.
- 기존 테스트 코드는 필요한 부분만 읽어 검증 범위와 누락을 파악한다. 테스트 파일이 있다는 이유로 통과했다고 주장하지 않는다.
- 실행이 필요한 의심은 테스트 시나리오와 기대 결과를 제안하고 별도 테스트 단계로 넘긴다. 검증을 요청받아 실행했으면 명령·결과를 짧게 기록한다.
- 테스트 파일을 새로 만드는 일은 설명에 자동 포함하지 않는다. 필요한 검증과 추가 테스트 제안은 분리한다.
- 코드상 확인, 자동 테스트, 브라우저 확인, 실기기 확인, 미확인 범위를 구분한다.
- 문제마다 실제 트리거와 결과, 위치, 근거를 제시한다. 재현하지 못한 의심은 확정된 버그와 구분한다.

## 결과 작성

기능 단위로 사용자 행동과 결과에서 시작한다. 중요한 결함·데이터 손실 위험·요구사항 차이가 있으면 먼저 알리고 관련 흐름을 설명한다. 문제가 없으면 억지로 지적을 만들지 않는다. 작은 변경은 몇 문장으로 끝내며 아래 항목을 고정된 보고서 양식으로 채우지 않는다. 인증·권한·데이터 삭제 등 영향이 큰 변경은 관련 선택과 근거를 더 자세히 제시한다.

설명은 핵심 흐름과 선택 이유를 중심으로 구성하고, 다음 중 필요한 내용을 덧붙인다.

- **바뀐 동작과 범위**: 요구사항에 반영한 내용과 차이·미구현 범위. 중요한 문제나 제약이 있으면 먼저 알린다.
- **중요한 선택**: 실제 대안이 있거나 복잡도·데이터·인증 등에 영향을 주는 결정과 이유·절충. 사소한 구현을 설계 성과처럼 나열하지 않는다.
- **직접 볼 코드**: 판단에 필요한 위치만 연결하고 무엇을 확인하면 되는지 설명한다. 변경 파일 전체를 읽기 목록으로 넘기지 않으며 필요한 지점이 없으면 생략한다.
- **검증과 공백**: 어떤 요구 동작을 어떤 수단으로 확인했는지 연결한다. 현재 실행 결과, 이전 결과, 코드상 판단과 미확인을 구분하며 테스트 통과를 전체 품질의 증거로 확대하지 않는다.
- **직접 해볼 흐름**: 사용성 판단이나 남은 기기 확인이 필요할 때 짧은 순서와 기대 결과를 제시한다. AI가 수행 가능한 검증을 사용자에게 넘기는 수단으로 사용하지 않는다.

설명의 깊이는 사용자의 질문과 변경 규모에 맞춘다. 요구사항 자료가 없거나 중요한 불확실성이 있으면 짧은 설명에서도 숨기지 않는다.

작성 후 사용자 행동부터 결과까지 흐름이 연결되는지, 중요한 선택이 필요한 상황을 먼저 설명했는지 확인한다. 파일·함수 소개나 추상적인 장점만 이어지는 부분은 동작과 이유가 드러나도록 고친다.

설명 중 발견한 문제나 대안은 다음과 같이 구분한다.

- **수정 필요**: 요구사항 누락, 잘못된 동작, 데이터 손실 등. 트리거·결과·코드 위치·수정 방향을 제시한다.
- **단순화 권장**: 동작을 유지하며 복잡도를 줄이는 구체적 방법과 효과. 수정 필요 문제와 같은 무게로 취급하지 않는다.
- **선택 사항**: 합리적인 여러 대안 사이의 취향·방향 차이. 선택하지 않아도 문제없는 항목임을 밝힌다.
- **확인 필요**: 자료나 실행 근거가 부족한 사항. 무엇이 확인되면 판단 가능한지 설명한다.

파일은 클릭 가능한 절대경로로 연결하고 지적에는 정확한 줄을 제시한다. 설명에 꼭 필요한 작은 코드만 인용한다. 요약에 중요한 위험을 생략하지 않되 반복·전체 파일 해설·형식 채우기는 피한다.
