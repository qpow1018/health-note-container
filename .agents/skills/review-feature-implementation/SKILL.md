# 구현 검토와 설명

사용자가 변경된 코드 전체를 뒤지는 시간을 줄이고, 중요한 동작·설계 선택과 근거를 골라 검토하도록 돕는다. AI의 자체 검토를 사용자 검토의 대체 증거로 삼지 않는다. 설명으로 평가를 대신하거나 구현을 옹호하지 않고, 더 단순한 방법도 검토한다.

## 요청 구분

- 프로젝트 지침에 따른 구현 후 검토에는 아래 검토 관점을 적용하고 간결한 완료 보고를 제공한다. 자세한 코드 해설은 의무가 아니다. 이번 구현에서 만든 결함은 요청 범위 안에서 수정하고 관련 검증을 다시 수행한다.
- "구현 설명해줘" 또는 기능의 구현을 이해하고 싶다는 별도 요청에는 핵심 흐름과 선택 이유를 더 자세히 설명한다. 요구사항 반영과 단순성·유지보수 평가도 포함한다.
- "코드 리뷰해줘"만 요청하면 이 스킬을 자동 적용하지 않는다. 일반 코드 리뷰로 버그·누락·위험과 수정할 부분에 집중한다.
- "결과 보고해줘"만 요청하면 이미 확보한 검토·검증 결과를 간결하게 요약한다. 이 요청만으로 검토나 검증을 다시 실행하지 않는다.
- 사용자가 이 스킬을 명시적으로 지정하거나 설명과 리뷰를 함께 요청하면 적용한다.

## 범위와 근거 확보

- 리뷰 요청은 기본적으로 읽기 전용이다. 보고서 파일 생성, 코드 수정, 자동 커밋은 사용자가 요청한 경우에만 진행한다.
- 현재 저장소의 AGENTS.md와 적용되는 프로젝트 스킬을 따른다. 다른 프로젝트의 구조·스타일을 강제하지 않는다.
- Git 상태와 diff를 확인하고 사용자가 지정한 기능·경로·커밋을 기준으로 범위를 좁힌다. 범위가 없으면 현재 변경을 우선 보고, 변경이 없다면 핵심 기능을 특정할 수 있는지 확인한다.
- 같은 기능의 진입점, 호출부, 상태, 저장/API 경계, 관련 테스트를 따라 읽는다. diff만 보고 기존 호출부와 동작을 추정하지 않는다.
- 변경 중인 파일을 되돌리거나 포맷팅하지 않는다. 설치·서버 실행·상태 변경을 수반하는 검증은 현재 권한과 사용자 요청 범위를 확인한다.
- 현재 대화, 사용자 제공 요구사항, 저장소 문서, 접근 가능한 승인 기록에서 기능의 합의를 찾는다.
- 다른 세션의 대화는 자동으로 전달되지 않는다. 없는 대화를 기억하거나 읽었다고 주장하지 않는다. 요구사항 자료가 없으면 코드 리뷰는 계속하되 '대화 반영 확인 불가'라고 표시한다. 중요한 판단에만 필요한 설명을 요청한다.
- 문서·커밋 메시지만으로 구현 완료를 인정하지 않는다. 실행하지 않은 동작은 코드상 판단과 런타임 확인을 구분한다.

## 검토 관점

### 기능과 요구사항

- 실제 사용자가 할 수 있는 동작, 미구현 범위, 실패 시 동작을 먼저 파악한다.
- 합의 항목별로 반영 / 일부 반영 / 미반영 / 확인 불가를 구분한다. 관련 경로와 동작 근거를 연결한다.
- 사용자 합의, 구현자가 선택한 정책, 리뷰어의 제안을 구분한다. 기존 코드에 있다는 이유로 사용자 합의라고 부르지 않는다.
- 요구사항 자료가 없으면 구현된 동작을 요구사항처럼 역으로 만들어내지 않는다.

### 설계와 이유

- 입력부터 검증, 상태 변경, 저장, 화면 반영까지 핵심 흐름을 평이한 말로 설명한다.
- 설명할 가치가 있는 선택만 다룬다. 모든 함수와 파일을 나열하지 않는다.
- 확인된 결정 이유와 코드에서 추론한 장점을 구분한다. 개발자의 실제 동기를 코드만으로 단정하지 않는다.
- 선택의 이점과 제약, 더 단순한 현실적인 대안이 있을 때 그 차이를 설명한다. 미래의 가상 기능만으로 복잡한 구조를 정당화하지 않는다.

### 정확성·단순성·유지보수

- 잘못된 입력, 중복 제출, 화면 이동, 비동기 실패, 기존 데이터 호환·보존 등 해당 기능에서 실제 가능한 실패를 검토한다.
- 불필요한 상태 복제, effect, 분기, 간접 호출, 단일 사용처 추상화, 과한 옵션을 찾는다.
- 같은 동작과 필요한 실패 처리를 유지하면서 더 단순하게 표현할 방법을 찾는다. 줄 수만 줄이려고 책임과 의미를 숨기지 않는다.
- 책임의 위치, 명명, 데이터 흐름, 실제 재사용을 평가한다. 취향이나 프로젝트와 무관한 유행을 결함으로 제시하지 않는다.
- 접근성, 긴 텍스트, 키보드·뒤로 가기·터치 등 사용 환경에 맞는 동작을 검토한다.
- 요청과 무관한 대규모 리팩터링을 권하지 않는다.

### 검증

- 타입·린트·빌드는 동작 테스트와 구분한다.
- 별도 설명·리뷰에서는 테스트·린트·타입 검사·빌드 명령, 개발 서버, 브라우저·실기기 검증을 자동 실행하지 않는다. 구현 작업 중에는 test-feature-behavior와 프로젝트 지침에 따라 필요한 검증을 수행한다. 이전 구현 요청의 검증 권한만으로 별도 리뷰에서 재실행하지 않는다.
- 기존 테스트 코드는 필요한 부분만 읽어 검증 범위와 누락을 파악한다. 테스트 파일이 있다는 이유로 통과했다고 주장하지 않는다.
- 실행이 필요한 의심은 테스트 시나리오와 기대 결과를 제안하고 별도 테스트 단계로 넘긴다. 검증을 요청받아 실행했으면 명령·결과를 짧게 기록한다.
- 테스트 파일을 새로 만드는 일은 리뷰에 자동 포함하지 않는다. 필요한 검증과 추가 테스트 제안은 분리한다.
- 코드상 확인, 자동 테스트, 브라우저 확인, 실기기 확인, 미확인 범위를 구분한다.
- 문제마다 실제 트리거와 결과, 위치, 근거를 제시한다. 재현하지 못한 의심은 확정된 버그와 구분한다.

## 결과 작성

기능 단위로 작성하고 사용자가 판단할 차이·문제를 앞에 둔다. 문제가 없으면 억지로 지적을 만들지 않는다. 작은 변경은 몇 문장으로 끝내며 아래 항목을 고정된 보고서 양식으로 채우지 않는다. 인증·권한·데이터 삭제 등 영향이 큰 변경은 관련 선택과 근거를 더 자세히 제시한다.

완료 보고에는 다음 중 필요한 내용을 선택한다.

- **바뀐 동작과 범위**: 요구사항에 반영한 내용과 차이·미구현 범위. 중요한 문제나 제약이 있으면 먼저 알린다.
- **중요한 선택**: 실제 대안이 있거나 복잡도·데이터·인증 등에 영향을 주는 결정과 이유·절충. 사소한 구현을 설계 성과처럼 나열하지 않는다.
- **직접 볼 코드**: 판단에 필요한 위치만 연결하고 무엇을 확인하면 되는지 설명한다. 변경 파일 전체를 읽기 목록으로 넘기지 않으며 필요한 지점이 없으면 생략한다.
- **검증과 공백**: 어떤 요구 동작을 어떤 수단으로 확인했는지 연결한다. 현재 실행 결과, 이전 결과, 코드상 판단과 미확인을 구분하며 테스트 통과를 전체 품질의 증거로 확대하지 않는다.
- **직접 해볼 흐름**: 사용성 판단이나 남은 기기 확인이 필요할 때 짧은 순서와 기대 결과를 제시한다. AI가 수행 가능한 검증을 사용자에게 넘기는 수단으로 사용하지 않는다.

자세한 구현 설명을 요청받으면 입력부터 화면 반영까지 핵심 흐름과 선택 이유를 확장한다. 요구사항 자료가 없거나 중요한 불확실성이 있으면 간결한 보고에서도 숨기지 않는다.

리뷰 결과 분류:

- **수정 필요**: 요구사항 누락, 잘못된 동작, 데이터 손실 등. 트리거·결과·코드 위치·수정 방향을 제시한다.
- **단순화 권장**: 동작을 유지하며 복잡도를 줄이는 구체적 방법과 효과. 수정 필요 문제와 같은 무게로 취급하지 않는다.
- **선택 사항**: 합리적인 여러 대안 사이의 취향·방향 차이. 선택하지 않아도 문제없는 항목임을 밝힌다.
- **확인 필요**: 자료나 실행 근거가 부족한 사항. 무엇이 확인되면 판단 가능한지 설명한다.

파일은 클릭 가능한 절대경로로 연결하고 지적에는 정확한 줄을 제시한다. 설명에 꼭 필요한 작은 코드만 인용한다. 요약에 중요한 위험을 생략하지 않되 반복·전체 파일 해설·형식 채우기는 피한다.
