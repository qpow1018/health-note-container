# 구현 완료 전 자체 검토

구현 요청의 일부로 변경을 다시 살펴 요구사항 누락·잘못된 동작·불필요한 복잡도를 찾아 수정한다. 사용자의 구현 설명 요청을 기다리지 않는다. 자체 검토는 사용자 검토나 실행 검증을 대체하지 않는다.

## 범위와 근거

- 구현 작업에 적용하면 이번 변경의 결함을 요청 범위 안에서 수정한다. 별도 검토 요청에서는 읽기 전용으로 판단하며, 코드 수정이나 테스트 실행 권한을 자동으로 확대하지 않는다.
- [공통 AGENTS.md](../../../AGENTS.md), 대상 프로젝트 지침과 관련 구현 스킬을 따른다. 웹·앱 중 변경한 영역과 영향을 받는 연결 흐름에 한정한다.
- 현재 Git 상태와 최종 diff를 확인해 이번 작업과 기존 사용자 변경을 구분한다. 진입점·호출부·상태·저장/API 경계·관련 테스트를 필요한 만큼 따라 읽는다. diff만으로 기존 동작을 추정하지 않는다.
- 현재 대화의 합의, 사용자 제공 요구사항, 관련 문서를 기준으로 판단한다. 사용자 합의와 구현 중 선택한 정책을 구분하고, 기존 코드나 새 구현에서 요구사항을 역으로 만들지 않는다.
- 요구사항 근거가 부족하면 확인 가능한 검토는 계속하되 해당 항목은 확인 불가로 남긴다. 중요한 정책을 임의 확정하지 않고 필요한 설명만 요청한다.

## 검토 기준

### 요구사항과 정확성

- 합의한 동작이 반영됐는지, 일부만 반영됐거나 빠진 범위가 있는지 확인한다. 입력부터 검증·상태 변경·저장·화면 반영까지 연결이 맞는지 살핀다.
- 잘못된 입력·중복 제출·화면 이동·비동기 실패·기존 데이터 보존 등 이번 기능에서 실제 가능한 실패 조건을 선택해 검토한다. 모든 변경에 같은 항목을 기계적으로 적용하지 않는다.
- 연결된 기존 호출부와 계약이 유지되는지 확인한다. 인증·권한·데이터 삭제·웹과 앱의 통신을 변경했다면 해당 경계를 함께 살핀다.
- UI 변경은 접근성·긴 텍스트·키보드·뒤로가기·터치 등 영향을 받는 사용 환경을 고려한다. 코드로 판단한 동작과 실행으로 확인한 동작을 구분한다.

### 책임과 단순성

- 코드의 위치·명명·데이터 흐름·실제 재사용이 맡은 책임에 맞는지 평가한다. 기존 패턴이라는 이유만으로 복잡한 구조를 유지하지 않는다.
- 불필요한 상태 복제·effect·분기·간접 호출·추상화·옵션을 찾는다. 제거했을 때 현재 필요한 어떤 동작이 깨지는지 확인한다.
- 같은 동작과 필요한 실패 처리를 유지하는 더 단순한 방법이 있으면 검토한다. 미래의 가상 기능으로 복잡도를 정당화하거나 줄 수를 줄이려고 책임을 숨기지 않는다.
- 취향 차이를 결함으로 취급하지 않고, 요청 밖의 대규모 리팩터링을 섞지 않는다.

### 영향 범위

- 변경한 각 부분이 요청 또는 이번 변경이 만든 결함 수정과 연결되는지 확인한다. 무관한 포맷 변경·의존성·설정·새 추상화가 섞이지 않았는지 살핀다.
- 이번 변경이 만든 미사용 코드만 정리하고 기존 사용자 변경을 되돌리지 않는다. 책임 경계나 동작 정책이 달라졌다면 관련 문서와의 일치도 확인한다.

## 발견한 문제와 검증

- 요구사항 누락·잘못된 동작 등 이번 구현에서 만든 결함은 허용된 요청 범위 안에서 수정한다. 단순화도 현재 동작을 보존하며 이번 변경 안에서 수행한다.
- 범위 밖 결함은 임의 수정하지 않는다. 실제 트리거·결과·위치·근거와 필요한 후속 작업을 보고한다. 실행 전 의심을 재현된 버그로 단정하지 않는다.
- 검증 방법과 실행은 [test-feature-behavior](../test-feature-behavior/SKILL.md)와 대상 프로젝트 지침을 따른다. 테스트 파일 추가나 전체 테스트 실행을 자체 검토의 고정 조건으로 삼지 않는다.
- 검토 후 수정한 부분은 다시 살피고 관련 검증을 수행한다. 이미 확보한 결과가 최종 코드에도 유효하면 반복하지 않으며, 검증 중 결함을 수정했다면 영향을 받는 부분을 다시 검토·검증한다.
- 코드상 확인·자동 테스트·브라우저·실기기 결과와 미확인 범위를 구분한다. 테스트 파일의 존재나 타입·린트·빌드 통과를 사용자 동작 전체의 성공으로 확대하지 않는다.

## 완료 판단과 보고

- 이번 요청의 요구사항 누락과 확인된 결함을 해결했는지, 남은 검증 공백이 무엇인지 판단한 뒤 완료를 보고한다. 해결하지 못한 문제나 중요한 불확실성을 숨기거나 완료한 것으로 표현하지 않는다.
- 요구사항과 확인된 결함을 처리하고 필요한 검증 근거를 확보했다면 검토를 마친다. 취향 차이나 가상의 개선 가능성만으로 재작성을 반복하지 않는다.
- 남은 결함·중요한 선택·검증 공백은 공통 지침에 따른 완료 보고에 반영한다. 검토 항목 전체를 고정 양식으로 채우거나 별도 보고서 파일을 만들지 않는다.
- 문제가 없으면 지적을 만들지 않는다. 단순화 제안·선택 가능한 대안·확인 필요 사항을 필수 수정과 구분한다. 자체 검토를 했다는 선언으로 실제 근거를 대신하지 않는다.
